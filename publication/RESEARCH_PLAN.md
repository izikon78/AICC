# AIN and AICC research programme

Izik Bachar, concept and research direction. Prepared with Codex assistance.
8 November 2026. Proposed programme, with no new experiment executed by this document.

## The decision this programme must resolve

AIN proposes that a learned computational representation can become the medium
of an agent's continuing work. AICC proposes that approved capabilities can be
discovered, bound and reused across that work. Their combined value would come
from reducing repeated expression, context processing and compatibility work
while preserving correct outcomes. A shorter printed program is one possible
consequence. The research target is the complete cost of maintaining useful
computation across requirements, changes, repairs and handoffs.

The theory begins with an already fluent optimized language and approved core.
That premise remains the starting point for the conditional analysis. The
experimental programme should then remove its simplifying assumptions one at a
time. It must determine whether useful results survive learned composition,
unfamiliar requirements, incomplete library coverage and operational change.
Building an extensive language or commons is unnecessary before those decisions.
A small experimental interface can make the relevant mechanisms observable.

The existing approved-core test supplies correct compositions and finds a
conditional position-demand reduction. Its ideal AIN, IR and Python interfaces
tie under the same encoding opportunities. The next programme must therefore
test both the general benefit of compact learned interfaces and any additional
benefit of a particular AIN structure. These are separate hypotheses with
different possible outcomes.

## Six phases with explicit gates

| Phase | Question and deliverable | Gate before expansion |
|---|---|---|
| 1. Reproduce and stress the theory | Independent counters, complete ledgers and sensitivity surfaces for vocabulary coverage, data exposure and repeated use | Resolve every unexplained accounting discrepancy and publish the assumptions under which the advantage disappears |
| 2. Establish operational fluency | Matched AIN, readable IR and compact Python agents using the same approved core, task interface and executable semantics | Each arm passes a frozen fluency gate before final evaluation; record adaptation cost separately |
| 3. Measure continuing work | Unseen build/change/repair/handoff chains with actual model and tool telemetry | Meet the declared correctness criterion and practical resource margin against the strongest matched control |
| 4. Test generalization and memory | New compositions, authored control flow, incomplete libraries, long histories and receiving-agent handoffs | Gains survive relevant workload strata; failures identify boundaries that can be reproduced |
| 5. Measure AICC lifecycle value | Ordinary-library versus governed-binding comparison with identical implementations and authority checks | Recurring measured savings exceed discovery, validation, invalidation and maintenance costs at observed reuse levels |
| 6. Replicate and decide | Independent implementation, second hardware/model setting and complete artifact release | Agreement within the declared uncertainty rule supports scaling; otherwise publish a bounded, neutral or negative result |

## A minimal next study

Start with a feasibility pilot of **24 four-stage chains per arm**, covering
event processing, versioned cache rules and asynchronous publication/retry.
Each domain contributes four reserved structural templates with two data
variants. Training and fluency examples use different templates. The pilot
estimates telemetry completeness, task difficulty and resource variation. It
does not serve as the final efficacy test.

Use three arms: compact Python, readable typed IR and the candidate AIN
interface. Give them identical approved implementations, task information,
feedback, tool access and decoding constraints. If numeric AIN and IR differ
only by spelling, report that as a spelling control. AIN's structure must have
an explicit difference before a structural advantage can be claimed.

Use matched copies of one accessible checkpoint for the first applied study.
Adapt each before evaluation, publish prior-language exposure and retain the
unadapted baseline. Run one training seed during feasibility, then plan three
independently seeded trainings per arm for the next development stage. A
pretrained adaptation study answers an applied question; a later matched
from-scratch study can isolate prior familiarity more cleanly.

For pilot planning, propose at most three model attempts per stage, 256 generated
positions per attempt and 180 seconds of model-plus-tool elapsed time per stage,
with the same feedback policy across arms. Feasibility measurements may revise
this envelope before the frozen study begins. A failed build, exhausted repair budget or unsuccessful
handoff remains an assigned failure. A receiving agent starts without the
sender's conversation and receives only the declared artifact, memory and
capability information. These are proposed protocol choices, not established
properties of AIN.

Before launching, freeze the model revision, context and output limits,
learning budget, hardware-hour ceiling, available GPU memory and maximum
complete-run duration. Measure a small instrumented batch on the available
RTX 3080 before extrapolating. Reduce the model or batch size equally when the
apparatus exceeds memory. Do not quietly reduce task coverage for one arm.

## From useful pilot to decisive evidence

The primary outcome is summed elapsed model-and-tool time across all assigned
attempts divided by correctly completed chains, accompanied by chain success
rate. Fix the concurrency and scheduling policy across arms. Retain complete
end-to-end elapsed time as well, including waiting and orchestration. Report
GPU time, CPU time and memory separately in their own units. Do not add CPU
seconds and GPU seconds into one work score without a declared conversion.
Keep training/setup, emitted-program execution and
lifecycle maintenance in separate ledgers. Report energy only where it is
actually measured, and financial cost only where an observed charge or
declared hardware-cost calculation supports it.

For a confirmatory design, begin planning around 72 unseen chains per training
seed, then determine the required final size from the development variability,
task-family dependence and declared decision margins. Three seeds and 72 cases
are design starting points, not a claim of statistical power. Reserve a new
final set and freeze its generator, selection method and analysis before
opening it. Repeated rows, token timings and data variants of one template
must not be counted as independent discoveries.

An example practical target is at least **10% lower elapsed time per correct
chain**, with a correctness loss no greater than **two percentage points**
against the strongest matched control. Those numbers are proposed decision
margins. The final protocol must select and justify them, together with a
paired uncertainty method respecting training seed and task family. If the
available budget cannot resolve the margins, label the study inconclusive
instead of treating point estimates as a decision.

Predefine three outcomes. Continue scaling when the correctness bound and
resource improvement criterion both pass. Reconsider the candidate when it
fails the correctness criterion or reliably consumes more work. Preserve a
neutral outcome when uncertainty spans useful benefit and meaningful harm.
No result from one bounded candidate establishes that every possible future
AIN succeeds or fails.

## The stress tests that give the programme depth

First vary where information lives. Compare resident data handles, selective
tool inspection and records included in context. Vary history length, memory
size and handoff frequency, charging every exposed operand and observation.
This tests whether the proposed advantage survives the information an agent
actually needs to make correct decisions.

Next vary reuse coverage. Include unfamiliar public functions, new literal
values, changed signatures and missing capabilities. Require some programs to
author a branch, bounded for/while loop or state transition from shared
primitives. Reserve genuinely different control-flow shapes. A catalogue of
whole-task solutions would conceal the composition problem this phase needs
to expose. Keep inference of new algorithms distinct from reuse of established
algorithms.

Cross representation with semantic vocabulary, structural constraints and
memory serialization in separate ablations. Give compact Python equivalent
aliasing and learned-interface opportunities. Measure whether improvements
come from structure, tokenization, constraints, reuse or their interaction.
The language label itself supplies no causal explanation.

## AICC as a lifecycle and deployment hypothesis

Hold library access constant in the representation study. Then cross the
successful interfaces with ordinary libraries and AICC bindings using the
same function bodies, contracts, caching opportunities and authority checks.
Include low-reuse work and revisions that invalidate existing approvals.
Measure discovery, compatibility checking, dependency changes, review effort,
failed bindings and repeated revalidation alongside successful invocation.

A record should distinguish semantic version, implementation identity,
declared effects and receiving-host authority. Public implementation reuse
must coexist with private policy and data. A transferred record must not
silently transfer authority. Test stale versions, revoked permissions,
interrupted work and incompatible receiving requirements. Production isolation
and authentication require their own implementation and evaluation.

Granularity is an experimental variable. Larger approved operations can
amortize dispatch and validation while delaying cancellation or hiding useful
intermediate feedback. Compare batch and incremental interfaces under equal
behavioral obligations. The useful boundary depends on the application.

Calculate lifecycle break-even only after recurring measured savings are
positive. With additional setup cost F and measured saving S per correct
repeated chain, F/S is a conditional reuse threshold in the same units. Report
the distribution of actual reuse and revision intervals. Training hours,
currency and abstract positions need separate calculations.

## Reproduction, interpretation and the scaling decision

Publish a preregistered protocol, hashes, environment, all attempts, raw
telemetry, failures and analysis code. Independent agents should preserve
their first implementation and output before comparing expected results.
Earlier exposure must be disclosed. Reproduce the frozen calculation first,
then test an independently implemented apparatus on new cases.

The programme can yield several useful conclusions. AIN-specific gains would
support further candidate development. Equal gains for AIN, IR and compact
Python would support a shared learned-interface mechanism. Useful AICC
lifecycle savings could justify capability governance even without an AIN
advantage. Persistent failure under strong matched controls would redirect
investment toward ordinary tooling. Each outcome contributes a concrete
decision about where further engineering is warranted.
